# A2A 分层主控架构

## 1. 设计结论

系统使用 A2A 作为跨客户端的标准通信层，但不采用完全平级的代理关系。
中转站在 A2A 任务和消息之上增加角色、授权与任务归属校验，从而形成：

```text
Human Owner > Controller > Reviewer / Worker
```

DeepSeek Harness 首先通过官方 ACP 接入。其他客户端只要能够提供 A2A、ACP
或可封装的任务接口，就可以通过独立适配器加入。

## 2. 角色

| 角色 | 默认主体 | 权限 |
| --- | --- | --- |
| Human Owner | 用户 | 批准、接管、终止、修改策略 |
| Controller | Codex | 规划、派工、追问、暂停、取消、验收 |
| Worker | DeepSeek Harness | 执行任务、报告状态、提交产物、申请信息 |
| Reviewer | 可选客户端 | 读取指定产物并返回审查意见 |

一个客户端可以具备多种技术能力，但每个会话只能按已授予的角色行动。

## 3. 协议边界

### A2A

A2A 负责代理发现、能力描述、多轮上下文、任务状态、消息和产物传输。
它是长期兼容层，不绑定 Codex、DeepSeek 或某一家模型服务。

### ACP

ACP 适配器负责将中转站任务映射为 DeepSeek Harness 的会话操作，包括创建或
恢复会话、选择模型、发送任务、监听更新、取消任务和关闭会话。

### MCP

MCP 留在每个代理内部，用于调用工具。主控端不应把“代理之间的对话”和“代理
调用工具”混为同一个权限面。

## 4. 权限模型

每个控制请求必须同时满足：

1. 发起者身份已经登记。
2. 发起者角色允许该动作。
3. 任务归属于该发起者可以控制的任务树。
4. 动作没有超过任务授予的工作区、网络和文件权限。
5. 高风险动作已经取得用户批准或一次性授权票据。

Worker 允许发送的主动消息只有：`status`、`result`、`question`、
`permission_request` 和 `failure`。Worker 发来的 `cancel`、`reassign`、
`change_role` 等控制消息必须被中转站拒绝。

## 5. 任务状态

```text
submitted -> accepted -> working -> input_required -> working
                              |             |
                              v             v
                           failed       cancelled
                              |
                              v
                         completed -> accepted_by_controller
```

`completed` 只表示执行端已经提交结果；只有主控端完成检查后，任务才能进入
`accepted_by_controller`。

## 6. A2A 扩展元数据

分层控制信息放入 A2A 任务的应用元数据，不修改 A2A 标准字段。建议命名空间：

```text
io.github.shenyouren.hierarchy
```

元数据至少包含主控侧关联任务 ID、父任务 ID、发起者、执行者、角色、允许动作、
权限范围、验收条件和时间信息。A2A 运行时任务 ID 由接收端按标准生成，二者通过
审计记录关联。结构草案见 `protocol/task-envelope.schema.json`。

## 7. 适配器接口

每个客户端适配器只需要实现以下能力：

- `discover`：返回客户端能力和可用模型。
- `start`：创建任务或会话。
- `send`：发送后续消息或补充资料。
- `status`：读取结构化进度。
- `cancel`：取消属于本中转站的任务。
- `artifacts`：读取结果和文件引用。
- `close`：释放会话资源。

中转站不依赖客户端自己的界面结构，也不通过模拟鼠标点击来控制执行端。

## 8. 第一版部署边界

- 中转站、Codex 和 DeepSeek Harness 均运行在本机。
- 服务仅监听 `127.0.0.1`。
- 凭据不写入仓库、任务正文或日志。
- 工作区权限默认使用只读或工作区写入，不默认授予全盘权限。
- 所有任务设置超时、输出大小限制和可恢复的状态记录。

## 9. 实施阶段

### 阶段 A：验证闭环

复用当前可运行的 DeepSeek 执行桥，验证派工、追问、回传和验收。

### 阶段 B：A2A 主控核心

实现代理登记、角色策略、任务树、状态机、审计日志和本地管理接口。

### 阶段 C：官方 ACP 适配

接入 DeepSeek Harness 官方 ACP，并将现有 Relay 保留为版本兼容和应急通道。

### 阶段 D：跨客户端验证

接入另一个支持 A2A 或 ACP 的客户端，验证只增加适配器即可替换执行端。

### 阶段 E：跨机器运行

在本地闭环稳定后，再增加 TLS、短期凭据、代理登记审批和网络访问控制。
